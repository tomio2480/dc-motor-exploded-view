## 📌 追記

報告された症状の主な原因は，描画の重さではなく，ドラッグ中に描画されない不具合だった．
詳しくは [ドラッグ中に表示が更新されない不具合の修正](2026-11-19-render-while-dragging.md) に記している．
この文書で加えた診断用の設定は，描画の重さを調べる手段として残している．

## 🧭 背景

- 利用者の Edge で，表示がカクついて滑らかに動かないと報告があった．
- 開発環境には GPU がなく，描画そのものにかかる時間を測れない．

## 🔍 調べたこと

### スクリプト側の処理時間

公開中のビルドで，1 フレームあたりのメインスレッドの処理時間を測った．
スクリプトは 0.2 ms から 1.3 ms，レイアウトは 0.6 ms 以下だった．
60 fps の 1 フレーム（約 16.7 ms）に対して小さく，スクリプトは主な原因ではないと判断した．

### 利用者の環境

`edge://gpu` の出力から，次のことが分かった．

- WebGL はハードウェアで動いている．GPU は内蔵の Intel Iris Xe である．
- 外付けの GPU はなく，GPU の選択ミスではない．
- ディスプレイは 1536×1024，表示スケールは 100% で，画素数は多くない．
- ブラウザーが Intel の GPU に対し，MSAA が遅いことへの回避策を適用している．

本サイトは 3D の描画で MSAA を有効にしており，これが有力な候補である．
解説欄の背景ぼかしも候補に残る．どちらが効いているかは，実機で測らないと分からない．

## ✅ 判断

- 推測で設定を変えず，実機で切り分けられる手段を先に用意する．
- URL のクエリで，アンチエイリアス・背景ぼかし・解像度の上限を切り替えられるようにする．
- `fps=on` で，フレーム間隔の中央値と描画先の画素数を画面へ表示する．
- 恒久的な対策は，実機での計測結果を見てから決める．
- 固定した解説の内容を，マウスを動かすたびに書き換えていた．
  内容が変わらないときは書き換えないようにした．これは原因によらず無駄な処理である．

## 🐞 実装中に得た知見

- フレーム間隔の平均は，操作の合間の短い停止に引きずられる．中央値を使うことにした．
- 描画を止めていた時間を除く上限を 250 ms にすると，遅い環境では値が出なかった．
  遅い環境こそ測りたいため，上限を 1000 ms へ延ばした．
- その後，1 フレームに 1 秒以上かかる環境では，値が出なかった．
  そこで，続けて描画した間隔は上限によらず数えるよう改めた．
  ただし，最初の描画は，シェーダーを用意するなどして長くかかりうる．
  この時間を数えると，遅い環境では最初の値が 0 fps になった．
  このため，最初の描画の直後の間隔には上限を当てる．
  描画を再開するたびに当てる案は，値の表示が遅れたため採らなかった．
  途中で描画を休んだ間隔にも，同じ上限が当たる．
  隠していたページへ戻った直後の間隔も同様である．
- WebGL のアンチエイリアスは，コンテキストの作成時にしか切り替えられない．
  このため，切り替えは URL のクエリで行い，読み込み直す形にした．
- lint が `describe` という名前の関数を，テストの `describe` と取り違えた．名前を改めた．
